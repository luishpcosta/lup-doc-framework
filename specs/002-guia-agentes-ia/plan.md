> HOW the spec will be implemented. Every functional requirement in `spec.md` must be addressed here. Cite `constitution.md` for any constraint you rely on.

## Technical Approach

Página única de conteúdo (`docs/guia-agentes-ia-app.md`), formato how-to, em português, dentro do Docusaurus `docs/` já existente (mesmo diretório de `docs/intro.mdx`). Não requer componente React nem interatividade — Markdown puro é suficiente (constitution: conteúdo em `docs/` é MDX, mas MDX aceita `.md` puro sem sintaxe JSX; não há necessidade de `.mdx` aqui porque não há JSX embutido). `sidebar_position` no front matter posiciona a página logo após `intro.mdx` na sidebar autogerada (`sidebars.ts` já usa `{type: 'autogenerated', dirName: '.'}`, então nenhuma mudança em `sidebars.ts` é necessária).

A página segue a ordem das 4 seções do briefing do usuário, mapeadas 1:1 para as FRs da spec:

1. **Resumo executivo** (FR-1/AC-1) — o que o guia cobre + tabela com `/sdd-harness-creator` e `/codefy` e seu papel.
2. **Preparação do repositório** (FR-2/AC-2, FR-3/AC-3, FR-4/AC-4) — brownfield vs. greenfield via `/sdd-harness-creator` (com recomendação de modelo forte no brownfield), exemplos de invocação; em seguida o uso contínuo de `/codefy` para encadear specs e propor regras em `AGENTS.md`/`CLAUDE.md`, com seus próprios exemplos.
3. **Uso no dia a dia** (FR-5/AC-5) — 5+ exemplos em linguagem natural, cada um uma frase curta em bloco de código copiável, cobrindo `/codefy`.
4. **Dicas para `AGENTS.md`/`CLAUDE.md`** (FR-6/AC-6) — modos de trabalho (rápido/faseado) e review automático de PR via hook.

## Architecture & Components

- `docs/guia-agentes-ia-app.md` — novo arquivo, único artefato de código desta feature. Front matter: `sidebar_position: 2` (depois de `intro.mdx`, que tem `sidebar_position: 1`), `title` explícito para a navbar/breadcrumb.
- Nenhuma mudança em `sidebars.ts` (sidebar autogerada já pega qualquer arquivo novo em `docs/`).
- Nenhuma mudança em `docusaurus.config.ts`, `src/`, ou `static/` — feature é puramente conteúdo.
- Blocos de exemplo de comando/prompt usam fences de código Markdown (` ``` `) sem syntax highlighting específico (são prompts em linguagem natural, não código-fonte), para diferenciá-los visualmente do corpo do texto.

## Constitution Compliance

- Princípio 1 (spec before code): esta feature segue o gate Specify → Clarify → Plan → Tasks antes de escrever `docs/guia-agentes-ia-app.md`.
- Princípio 5 (fidelidade ao design system): página usa apenas Markdown padrão do Docusaurus/Infima — sem CSS/cores hardcoded, então herda automaticamente os tokens de `src/css/custom.css` (fontes, paleta, dark mode).
- Quality Bar: `npm run typecheck` e `npm run build` obrigatórios; como é uma página nova visível no site, verificação visual manual (light e dark mode) via `npm run build && npm run serve` antes de marcar a task como `done`, conforme regra do `CLAUDE.md` do projeto ("UI changes need eyes on them").
- Test framework: nenhum (constitution — site de conteúdo); `npm run build` com `onBrokenLinks: 'throw'` é a verificação de regressão aplicável aqui.

## Key Decisions

| Decision | Choice | Alternatives considered | Rationale |
|---|---|---|---|
| Formato do arquivo | `.md` (Markdown puro) | `.mdx` com componentes React | Conteúdo é só texto/listas/código — não há necessidade de JSX; `.md` é mais simples e ainda processado pelo mesmo pipeline docs do Docusaurus |
| Localização | `docs/guia-agentes-ia-app.md`, mesmo nível de `docs/intro.mdx` | Subpasta `docs/agentes-ia/` com múltiplos arquivos | Spec exige explicitamente "única página" (FR-7); uma subpasta sugeriria multi-página na sidebar |
| Sidebar | `sidebar_position: 2` no front matter, sem editar `sidebars.ts` | Definir sidebar manualmente em `sidebars.ts` | `sidebars.ts` já usa `autogenerated`; adicionar uma entrada manual quebraria esse padrão sem necessidade |
| Origem das skills `/codefy`/`/blueprintfy` | Não citada no texto | Citar como nota/rodapé | Pedido explícito do usuário (FR-8) |
| Escopo do guia (tipo de repositório) | Manter exemplos de código como estão; deixar o escopo explícito no nome do arquivo, título e abertura | Generalizar os exemplos para valer também para repositórios de conteúdo/documentação | Usuário observou que o guia é específico para repositório de aplicação; escolheu explicitar em vez de generalizar (FR-9) |
| Modelo/técnica de escrita | Diátaxis How-To Guide + minimalismo instrucional (Carroll) | Runbook/Playbook operacional; Reference (lookup table) | Já era o gênero autodeclarado do guia; resolve a mistura de registros (explicação/how-to/reference) sem violar a página única (FR-7) nem perder a persona de quem ainda avalia adotar o fluxo (FR-10) |
